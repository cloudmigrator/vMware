# Secure Boot Scripts Working Mechanism

## What the automated script does — step by step

[0] Preflight
    Checks ESXi version, HW version, firmware, Tools status, DC, BitLocker
    Nothing is touched until all checks pass
    If any check fails → hard stop, VM untouched

[1] Power off
    Clean shutdown via vSphere API
    Waits for confirmed PoweredOff state before proceeding

[2] Snapshot
    Full VM snapshot before any change
    This is your complete rollback point
    If anything goes wrong after this → Rollback mode restores everything. 
    > [!WARNING] BE CAREFUL ABOUT DB SERVERS

[3] NVRAM rename  (.nvram → .nvram_old)
    Done via vSphere FileManager API (not inside the guest)
    The original NVRAM is preserved as .nvram_old
    ESXi generates a brand new NVRAM file on next boot
    This is the key step -- new NVRAM contains 2023 KEK/DB certs
    because ESXi 8.0.2+ ships with updated cert templates

[4] Power on + cert verification
    ESXi regenerates NVRAM with current cert templates
    Script waits for Tools + guest ops agent
    Reads actual DB and KEK bytes from UEFI via Get-SecureBootUEFI
    Confirms 2023 certs are physically present before proceeding

[5] Registry fix
    Runs as SYSTEM via schtasks wrapper (avoids UAC filtering)
    Clears stale UEFICA2023Status tracking keys
    Sets AvailableUpdates = 0x5944 (tells Windows all cert slots need updating)
    Sets WindowsUEFICA2023Capable = 2

[6] Reboot + task trigger
    Triggers \Microsoft\Windows\PI\Secure-Boot-Update
    This is a built-in Microsoft task -- script just calls it, doesn't replace it
    Task updates Boot Manager and writes final UEFICA2023Status = Updated

[7] Verification
    Re-reads DB, KEK, registry status
    AvailableUpdates = 0x0000 = definitive completion signal
    Reports exactly what was found

[8] PK check
    Reads raw PK bytes from UEFI
    Valid_WindowsOEM / Valid_Microsoft = no action needed
    Valid_Other (ESXi placeholder) = enrollment needed

[9] PK enrollment  (replaces the entire manual FAT32 disk process)
    Sets uefi.secureBootMode.overrideOnce = SetupMode on VMX
    This is a single-use ESXi 8 flag -- self-clears after one boot
    No persistent security change to the VM
    Reboots VM -- UEFI enters Setup Mode (PK-less state)
    Copies WindowsOEMDevicesPK.der into guest via Invoke-VMScript
    Runs Format-SecureBootUEFI | Set-SecureBootUEFI inside Windows
    Clears the VMX flag (even if enrollment fails)
    Reboots and reads PK bytes to confirm Valid_WindowsOEM

 

## Safety analysis — what could go wrong and what protects you

Risk 1 — VM won't boot after NVRAM change Protection: snapshot exists before any change. Run -Rollback and the VM is back to exactly where it was. .nvram_old is preserved, snapshot is reverted, VM powers on. Be very causious for DB servers. 

Risk 2 — overrideOnce flag left on VMX Protection: the script clears it in finally{} — meaning it gets cleared even if PK enrollment throws an exception. The manual method uses allowAuthBypass = TRUE which is persistent and broader — it bypasses all auth, not just PK enrollment.

Risk 3 — Wrong cert enrolled Protection: the cert path (-PKDerPath) is validated before the script starts. The cert being enrolled is WindowsOEMDevicesPK.der from Microsoft's official secureboot_objects repository — the same cert used in the manual method.

Risk 4 — Script crashes mid-run, VM left in bad state Protection: every catch block checks $rec.SnapshotCreated and retains the snapshot if true. The -Rollback mode handles recovery. The smart resume logic means re-running picks up from where it left off rather than repeating completed steps.

Risk 5 — Guest ops agent contacted at wrong time Protection: Wait-GuestOpsAgent probes with a trivial command in a retry loop before any Invoke-VMScript that matters. Tools status toolsOk is necessary but not sufficient — the agent probe is the actual gate.

Risk 6 — Run against wrong VMs by mistake Protection: -PreflightOnly mode lets you validate the full target list with zero changes. DCs are excluded at preflight. BitLocker is detected and blocked. EFI + Secure Boot enabled is a hard requirement.

The one thing the script cannot protect against
If the ESXi host itself is below 8.0.2, the new NVRAM generated by step 3 will NOT contain 2023 certs — because the cert templates in ESXi firmware are what populate the new NVRAM. The preflight check blocks this, but if you somehow bypass preflight or the host version check is wrong, you'd get a VM with a blank NVRAM and no 2023 certs. The snapshot covers you even then — rollback restores the original NVRAM immediately.
